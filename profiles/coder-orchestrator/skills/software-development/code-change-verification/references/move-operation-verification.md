# Move-operation verification

Use for board/job/task moves that can target an existing destination or create one.

## Focused regression pattern

1. Create an authenticated owner, board, project, and source column.
2. Create a job in the source column, including at least one non-todo lifecycle state if the operation permits it.
3. POST the move with an existing destination and assert HTTP success plus the persisted lane/column change.
4. POST the move with a new destination name and with the UI sentinel payload (for example `{"columnId":0,"newColumnName":""}`). Assert HTTP success, a non-zero returned destination ID, a non-empty generated fallback name, the created destination row, and the job’s persisted lane/column change.
5. Exercise the destination-not-found probe carefully: if the SQL query is expected to return no rows, normalize that expected result to nil before continuing the transaction. Otherwise a stale `sql.ErrNoRows` can make a later valid operation fail with a misleading target-validation response.
6. In the frontend, test the selection transition itself: choose `<New column>`, assert the conditional name field appears, and assert the submitted body uses the new-destination sentinel rather than the previously selected column ID.
7. Refresh destination options when opening the move dialog so stale board state cannot submit an invalid target. Keep the dialog open and display the API error on failure.

## Runtime-freshness escalation

When tests pass but the user says the deployed operation still fails, check deployment before writing another source fix:

1. Inspect the running service definition and resolve its exact executable (`ExecStart`), working directory, environment file, frontend document root, and database.
2. Compare executable and frontend artifact timestamps/hashes with the current build. A pushed commit does not update a running binary or static bundle.
3. Build from the correct module roots: compile the backend to the exact `ExecStart` path and run frontend package commands from the directory containing `package.json`.
4. Restart the service, wait briefly, and verify it remains active. Fetch public HTML and confirm its asset hash changed to the newly built bundle.
5. Exercise the exact authenticated public API payload generated by the UI. Re-fetch board state and assert the source is empty and the job appears under the returned destination ID.
6. Browser interaction remains the strongest UI proof. If unavailable, report authenticated public API persistence and deployed-asset evidence precisely; do not relabel it browser E2E.

## Verification hygiene

Run focused backend and frontend tests through a directly executed `/tmp/hermes-verify-*` script when workspace verification is not automatically registered. Use `mktemp`, a cleanup trap, and verify that the test runner executed at least one selected test—zero exit with all tests skipped is not evidence. Run the proportionate frontend build separately or in the same script.

Do not claim browser E2E from API tests, an asset hash, or a build. Keep each evidence boundary explicit.
