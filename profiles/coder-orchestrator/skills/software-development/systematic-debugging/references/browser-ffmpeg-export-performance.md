# Browser FFmpeg Export Performance Triage

Use when a web video editor/exporter feels slow, especially when using `@ffmpeg/ffmpeg`, FFmpeg WASM, or browser-only local processing.

## Root-cause checklist

1. Inspect the actual FFmpeg args generated by the app, not just the UI copy.
   - `-c:v libx264`, `-c:a aac`, CRF/preset flags = full re-encode.
   - `-c copy` = stream copy/remux, usually much faster.
2. Check seek placement:
   - `ffmpeg -i input -ss START ...` seeks after input open. More accurate, but can decode from earlier frames and is slower.
   - `ffmpeg -ss START -i input ...` seeks before input open. Much faster, but keyframe-oriented unless re-encoding after seek.
3. Check whether each slice runs as a separate sequential job. Repeating decode/re-encode per clip scales roughly with slice count and source position.
4. Check whether the browser writes the whole source into the WASM virtual FS before export. Large files add memory pressure and startup delay.
5. Separate ZIP packaging cost from render cost. ZIP mode is rarely the main bottleneck if clips are already re-encoded first.

## Quick benchmark pattern

Create or use a representative source video and compare three modes:

```bash
# Current-style exact export: seek after input + re-encode
ffmpeg -i source.mp4 -ss 45.000 -t 5.000 -avoid_negative_ts make_zero \
  -c:v libx264 -preset veryfast -crf 18 -c:a aac -movflags +faststart exact.mp4

# Fast export: input seek + stream copy
ffmpeg -ss 45.000 -i source.mp4 -t 5.000 -avoid_negative_ts make_zero \
  -c copy -movflags +faststart fast-copy.mp4

# Middle ground: input seek + faster re-encode
ffmpeg -ss 45.000 -i source.mp4 -t 5.000 -avoid_negative_ts make_zero \
  -c:v libx264 -preset ultrafast -crf 23 -c:a aac -movflags +faststart fast-reencode.mp4
```

Use real timings before recommending architecture changes. In one 720p/60s synthetic test, current-style exact re-encode took ~5.8s for a 5s clip, stream copy took ~0.1s, and input-seek ultrafast re-encode took ~1.9s. Treat those as directional, not universal.

## Fix decision tree

- If users accept keyframe-near cuts: make **Fast Export** the default using input seek + `-c copy`.
- If users need exact frame boundaries: keep **Exact Export** as an explicit slower mode using re-encode.
- If videos are long, exports are batch-heavy, or reliability matters: move export to server-side/native FFmpeg with a job queue.
- Native mobile can help, but it is not the root fix if the algorithm still re-encodes every clip sequentially. Prefer changing the export strategy first.

## Implementation pattern for browser-only product fixes

When the app must stay web-only, a durable fix is to expose the trade-off instead of silently keeping the slow path:

- Add an `ExportStrategy`/equivalent setting with **Fast** as the default and **Exact** as the explicit slower mode.
- Fast command preview/execution should show input seeking before the input and stream copy, e.g. `ffmpeg -ss START -i input -t DURATION -c copy ...`.
- Exact command preview/execution should preserve frame accuracy with post-input seek and re-encode, e.g. `ffmpeg -i input -ss START -t DURATION -c:v libx264 ... -c:a aac ...`.
- UI copy must clearly state that Fast avoids re-encoding and may snap to nearest keyframe; Exact re-encodes for frame-accurate boundaries and is slower.
- Regression tests should assert the argument order and codec flags for both modes, plus the UI default/active controls.
- Deployment verification should fetch the public JS bundle and grep for mode markers such as `Fast Export`, `stream copy`, and `Exact mode`, because Vite `index.html` often contains only an empty root.

## UX recommendation

Expose performance/accuracy trade-offs directly:

- Fast Export: very fast, may cut at nearest keyframe.
- Exact Export: frame-accurate, slower because it re-encodes.
- Server/Cloud Export: best for long files and batches, requires upload/processing queue.
