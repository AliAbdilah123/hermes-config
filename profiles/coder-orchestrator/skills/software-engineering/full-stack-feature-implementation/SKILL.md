# Full-Stack Feature Implementation

Use this skill when the user asks to update an existing project with a real implementation rather than stubs, mocks, or a plan. The goal is a working artifact backed by tool output.

## Focused UI and embedded-build verification

## Browser modal history

For modal or inspector behavior involving the browser Back button, treat the modal as a history layer rather than a route change:

1. Write a focused UI regression test first. Preserve a realistic path/query, open the modal, trigger `popstate`, and assert both that the modal closes and that the underlying location is unchanged.
2. On open, push a same-URL history entry and register a `popstate` listener that closes the modal. Remove the listener on cleanup.
3. Route ordinary modal-close actions through `history.back()` so the synthetic entry is consumed instead of leaving a duplicate history step.
4. Verify the focused test separately before the full suite. If the full UI suite exposes unrelated DOM cleanup leakage, report it accurately rather than weakening the focused regression.

See `references/browser-modal-history.md` for the minimal React pattern and verification checklist.

## Verify the executable actually deployed

Before rebuilding or replacing a service executable, inspect the service manager's actual `ExecStart` path and build or copy to that exact location. A successful build elsewhere plus a successful restart can silently leave the old embedded frontend running.

After restart, use a bounded readiness retry instead of assuming the first request will succeed. Verify both process health and a release-specific marker: for an embedded SPA, fetch the live HTML and confirm its generated asset filename/hash matches the build output. A generic HTTP 200 is insufficient proof that the new release is serving.

Treat service verification and public-route verification as separate gates. A healthy backend at `127.0.0.1:<port>/` does not establish which hostname or nginx path is public. Inspect the active reverse-proxy configuration, then request the exact public URL and verify both its status and the same release-specific marker. Never infer that the app is served at a domain root merely because the direct service root works, and never present an unverified fallback URL as the project's public link. If the expected public route returns 404 and no configured public route can be proven, report deployment health separately and state that the public URL remains unverified.

For account-to-workspace integration migrations, including API authorization, execution-path tracing, restart reconciliation, UI relocation, and isolation tests, see `references/workspace-scoped-provider-settings.md`.

See `references/systemd-embedded-spa-verification.md` for the concise verification sequence.

For cross-cutting pending states on API-triggering controls, use `references/async-action-loading-feedback.md` to audit async controls, implement accessible duplicate-safe feedback, test promise lifecycles, and verify embedded deployment.

## Preserve semantic UI categories across the full stack

When changing how mixed timelines, activity feeds, or histories render, do not classify entries only at the presentation layer from generic payloads. Trace the event from producer to API to UI and preserve a stable semantic kind for each visual category (for example, conversational replies versus operational output/status history).

1. Give newly produced events an explicit semantic kind at the shared producer.
2. Keep historical records compatible at the read boundary with a narrow mapping based on trustworthy persisted context; avoid a destructive migration when query-time mapping is sufficient.
3. Apply styling from that semantic kind: participant messages retain chat affordances, while machine/status history can remain subdued text.
4. Exercise both halves in one focused regression check: conversational entries still use bubbles, and non-conversation entries do not.
5. Check every API path that returns or streams the event type so detail views, polling, and live streams agree.

Pitfall: converting every event to a generic `output` kind can make later visual cleanup erase meaningful conversation styling. Styling every output as a reply instead turns logs into fake chat. Preserve the distinction at creation and normalize legacy data only at read boundaries.

## Preflight: determine whether the feature already exists

Before changing code or delegating implementation, inspect the current branch, recent history, relevant source, tests, and generated/deployed assets. A request may describe work that has already landed since the user's last context update.

If the requested behavior already exists:

1. Do not create a redundant diff, duplicate test, empty commit, or cosmetic rewrite merely to appear active.
2. Run the feature's targeted tests and the appropriate regression suite.
3. Build the production artifact when the project embeds or copies frontend assets. If the backend binary embeds that directory (for example via Go `embed`), rebuild the backend after the frontend copy; the previously built binary still contains the old asset snapshot.
4. Confirm the implementing commit is an ancestor of the tracked remote branch.
5. Verify the live experience rather than relying only on source inspection. After restart, fetch the app HTML and confirm it references the new hashed assets, then fetch one referenced asset and check for a distinctive marker from the change. A successful restart alone is not deployment proof for an embedded SPA.
6. Report that it was already implemented, identify the existing commit, summarize verification, and include the public link when required.

This is completion by verification, not a skipped implementation. Keep the final report precise and never claim a new change was made when the working tree remained clean.

For cases where current source contains a frontend change but the opened app does not show it, especially when frontend assets may be compiled into a backend binary, follow `references/embedded-frontend-binary-deployment.md`.

## Dirty-tree and agent-side-effect audit

For broad review-driven work in an already-modified repository, capture the pre-run HEAD, branch, status, diff stat, and modified-file list before delegating. Existing changes may be the implementation in progress; preserve and assess them instead of resetting or rebuilding them.

After the coding agent exits, inspect both the working tree and every commit since the captured HEAD. Do not assume a small final `git diff` means little changed: an agent may commit despite a no-commit instruction. Independently verify that prohibited artifacts (such as CI workflows explicitly excluded by the user) were not created, rerun all stack checks directly, and only then deploy/push.

## Auditable lifecycle actions

When a feature asks for status-change, retry, archive, or similar lifecycle history in an existing timeline:

- Reuse the existing event/run model instead of creating a parallel audit-log abstraction.
- Record explicit domain events at the same transaction boundary as the state mutation. Status events should carry both old and new values; retries and archives should have their own event kinds rather than being inferred later.
- Treat “archive history remains visible” as incompatible with hard deletion. Prefer a soft-archive flag, exclude archived records from active board/list queries, retain runs/events, and keep the authorized detail endpoint readable for timeline inspection.
- Block further mutations on archived records and preserve existing user/workspace ownership checks for archived-detail access.
- Add tests first for event contents, history retention, active-list exclusion, archived mutation rejection, and cross-user denial. Rebuild and commit generated frontend assets when the repository tracks embedded build output.

## Completion discipline for broad review-driven implementations

When implementing a long audit/PRD checklist across backend, frontend, workers, migrations, and deployment:

- Convert every source finding into an explicit scope ledger and mark exclusions (for example, “all items except CI”) before delegating. Re-read the full source artifact; do not let the latest or easiest finding narrow the implementation.
- A coding agent’s summary is not verification. After it exits—or if it is interrupted—inspect `git status`, compile/test each runtime directly, and search for half-written call sites or newly referenced undefined helpers. An interrupted reviewer may leave additional edits despite reporting only an error.
- Run a production build of compiled services in addition to tests. Test binaries and cached builds can miss a symbol used only by the real entrypoint; use the actual deployment build command before installation.
- Treat deployment configuration as part of the feature when new required secrets or protocol fields are introduced. Generate independent secrets, update both ends of signed integrations, remove insecure service-level overrides, reload services, restart, and verify health plus the public route.
- Before committing, rerun the complete relevant verification chain after the final edit, then `git diff --check`. Commit and push only that verified state.
- After deployment, if the workspace shows unexpected uncommitted changes, report them precisely and do not silently include or discard them.

## Workflow

1. **Locate the project and inspect context**
   - Check the project tree, current branch/status, package scripts, backend/frontend layout, docs/specs, and recent commits.
   - Search for `TODO`, `stub`, `mock`, `placeholder`, `not implemented`, and integration-specific feature flags.
   - If the user references past work or an ongoing project, use session recall before asking them to repeat details.
   - When the user asks to use kanban/subagents for a build, create a session `todo` board first for your own turn planning, but create **real Hermes Kanban** cards with `hermes kanban` if the user expects to see tasks in the Kanban UI. Keep final integration, test/build fixes, deployment, and public verification in the parent agent. See `references/kanban-subagent-web-mvp-build.md` and `references/hermes-kanban-real-board.md`.
   - When creating a new local project from the boilerplate and implementing a PRD-backed kanban/delegation app, copy the boilerplate excluding `.git`, `node_modules`, build output, and live DB files; update Vite base, nginx paths, service name, DB path, and use PRD-facing tests before implementation. See `references/boilerplate-to-local-project-kanban-delegation.md`.
   - When creating a fresh local Go + SQLite + Vite app, add `.gitignore` before committing, use explicit JSON tags on every Go DTO field, check port availability before systemd/nginx wiring, and verify new domain vhosts with a local `Host:` header before public smoke. See `references/new-local-go-vite-project-deploy-pitfalls.md`.
   - When creating a sibling/variant project by copying an existing deployed project (not the boilerplate), rsync excluding `.git`, `node_modules`, `dist`, `data`, and `bin`; then batch-replace slug, port, module name, env var names, data dir, and DB filename across all source files. Watch for the double-replace pitfall and check for port collisions before deploying. See `references/sibling-project-copy-identity-rename.md`.
   - When adding a new plugin to the boilerplate itself (new feature as a plugin), follow the plugin anatomy: backend `plugin.go` + `handlers.go` + `migrations/*.sql` wired into `cmd/app/main.go` (routes + migrations) and `cmd/app/plugin_<name>.go` (factory); frontend `plugin.ts` + page components wired into `App.tsx`. See `references/boilerplate-plugin-anatomy.md`.
   - When removing built-in execution providers/delegates, trace and delete the complete coupling: settings selector/API, user default and job snapshot columns, scheduler branches, adapters/config, built-in discovery entries, DTO/UI labels, tests, docs, and generated assets. A selector column with one possible value is obsolete state. Preserve independent custom tools only when still useful, and rebuild legacy SQLite tables transactionally with a migration test that proves unrelated/custom-tool data survives. See `references/removing-built-in-execution-providers.md`.
   - When a job detail modal must let the user reply to a running CLI/agent session, add a state-neutral authenticated comment endpoint, send literal text to the persisted active process session, record a timeline event, and reuse the existing SSE refresh path. Keep blocked-only approval/input state transitions separate. See `references/live-job-session-comment-composer.md`.
   - When an agent/job app needs chat bubbles, live board state, persistent completion/error notifications, an infinite-scroll bell menu, and clickable toasts, reuse existing job events and the existing job-detail modal; add idempotent owner-scoped notification persistence with cursor pagination, and use authenticated user-level SSE or short polling as fallback. Do not toast historical rows on initial load, and honor “Mark unread” literally. Trace `createRoot(...).render(...)` before editing so the feature lands in the active app shell rather than a legacy duplicate, and verify the authenticated DOM—not only bundle strings. See `references/job-notification-center-and-chat-live-updates.md`.
   - When adding retry/reprocess to a job detail modal, model it as a completed-job transition (`done -> todo`), clear terminal completion metadata, preserve attempt history, and let the existing scheduler create the next run. Reject retry from non-done states and keep blocked-session approve/input/cancel controls semantically separate. See `references/job-detail-reprocess-action.md`.
   - When a completed job must accept a reply, do not send to its dead process session. Record the reply on the prior timeline, persist it as a pending follow-up, transition `done -> todo`, and let the scheduler create the fresh run and move it to `in_progress`; clear the pending reply only on successful claim. Build embedded frontend assets before compiling the backend binary. See `references/reply-to-completed-job-reopens-execution.md`.
   - When adding Archive to a job detail modal without an existing archive model, use terminal-job deletion as the minimal path: owner-scoped `DELETE`, reject active jobs, reuse refresh/close, and prove dependent runs/events are removed. Do not trust SQLite cascades across pooled connections without a test; use an explicit child-to-parent transaction when needed. See `references/job-detail-archive-action.md`.
   - When the user asks “where is X?” in a full-stack app, return a location map instead of a generic explanation: identify route registration, page/component, client/provider setup, env/config gate, backend middleware/API verification, and any public URL path. Use exact paths and line references; inspect only key names/examples for auth/env and never print secrets.
   - When planning or implementing general-purpose AI chat/agent/usage features, prefer a unified `ai_requests` parent model for both chat requests and agent runs when metadata overlaps; store agent timeline/tool-call detail in a child `ai_request_steps` table. See `references/ai-request-agent-run-unified-model.md`.
   - When a stateful chat provider such as Hermes returns a `session_id`, persist it on the internal job/conversation/AI-run boundary, omit it on the first turn, reload and send it on later turns, and prove continuity with a fake provider plus DB-backed test. Wire the helper into the real authenticated execution route; a tested but unused helper is not delivery. See `references/chat-provider-session-continuity.md`.
   - When the task is an update to a PRD/review document or previously generated HTML artifact, find and edit the canonical file under the project `docs/` path rather than creating a new duplicate. Preserve the public-review convention: publish it under `/prd/<name>` via the nginx-served PRD directory/symlink, then verify both HTTP 200 and that the public response contains the newly requested content.
   - When planning or amending a bounty/gig marketplace app, keep the domain model exact: posters approve proposals, bank details remain user profile/onboarding data unless explicitly tied to payment, manual payments stay outside the app, and quota/duration/status/image rules must be spelled out in both backend and frontend requirements. See `references/bounty-marketplace-plan-amendments.md`.
   - When implementing a PRD bounty/gig marketplace into an existing Go + SQLite + Vite app, inspect old job/proposal schema first and avoid table-name collisions, grouped Go JSON tag bugs, and live DB additive-migration gaps. See `references/prd-bounty-marketplace-into-existing-go-vite.md`.
  - When the user provides a design from an external tool (Google Stitch, Figma export, etc.) and wants to apply it to an existing page, follow the design-driven redesign workflow: obtain the design source (Google Stitch is auth-gated — ask user to export HTML), analyze the design's tokens (colors, fonts, layout, interactions), cross-reference with the project's existing CSS variable system, ask adaptation questions via `clarify` (color/font strategy, interaction model, layout, what to preserve), create a planning HTML artifact with a mockup using the EXISTING design system, then implement preserving all data flows. See `references/external-design-driven-page-redesign.md`.
  - For external designs with a strong visual metaphor (wallet pockets, tickets, stacked cards, physical objects), preserve the source object's structure before token mapping. Do not collapse full cards into strips or otherwise change the metaphor just to fit the existing layout. If fidelity is corrected after user feedback, revise the review artifact before implementation and consider adding a rejected-vs-approved comparison. See `references/external-design-wallet-pocket-fidelity.md`.
   - When the user corrects the product model after reviewing the current app (for example, saying an arbitrary numeric score is not useful), treat it as a full product-concept correction: update the review artifact first with the user's exact term, then implement the data model/API/UI changes and verify public copy. For replacing opaque lead scores with explainable opportunity tags, follow `references/explainable-opportunity-tags.md`.
   - When implementing WhatsApp/outreach actions in a CRM app, treat sending a message as a CRM event: update early-stage business/lead status to contacted, create a contacted lead if none exists, handle worker/provider failures as queued messages without losing the CRM transition, and test the status sync first. See `references/whatsapp-crm-status-sync.md`.
   - When implementing scraped local-business data workflows in Go + SQLite + Vite apps, build the loop as scrape schema detection → normalized business/import_rows audit → explainable potential tags → segment work queues → idempotent segment-to-CRM, then verify backend tests, frontend build, public bundle markers, and live `/segments` smoke. See `references/scrape-import-tags-segments-go-vite.md`.
   - When a user asks to implement remaining PRD gaps after an audit, ship thin vertical slices for each missing area (DB table + authenticated route + native UI + smoke) rather than a speculative rewrite; keep enrichment/audit/campaign/job/report workflows deterministic/manual-first unless an external provider is explicitly configured. See `references/prd-gap-completion-go-vite.md`.
   - When delegated PRD-gap work adds a new domain model beside legacy runtime tables, verify the actual diff rather than the worker summary, use explicit mapping foreign keys instead of shared numeric IDs, and run a fresh-account live creation-chain smoke after deployment. See `references/prd-gap-completion-delegation-and-legacy-id-mapping.md`.

- Treat env values as present but secret
- Do not read or print secret-bearing `.env` contents.
- Prefer `.env.example`, config code, and key-name-only inspection when needed.
- When asked to populate missing env variables, audit key names from source/config loaders and env files without printing values; exclude generated directories like `dist` and `node_modules`, add safe placeholders/comments for missing optional keys, and verify no referenced keys remain missing.
- If the project has provided env values but code does not load them, implement safe env loading without leaking values.
   - When the user asks what runtime app/client ID or public integration config is used, inspect the deployed service definition and config-loading aliases, then extract only allowlisted non-secret keys (`*_APP_ID`, `*_CLIENT_ID`, redirect URIs, public URLs, graph versions). Never dump full env files or expose secrets.

3. **Replace stubs with real integration paths**
   - When adding a remote OpenAI-compatible agent API as a selectable execution provider beside local CLI delegates, keep secrets write-only, validate URL/key conditionally, reuse the existing run/event lifecycle, test with a fake HTTP server, and rebuild embedded frontend assets before the Go binary.    - Identify where mocks/degraded behavior are gated by config.

   - Preserve local degraded/mock paths only as explicit fallback behavior for missing config; do not let fallback shadow provided env values.

4. **Verify both sides of the stack**
  - Run frontend typecheck and production build.
  - For admin/settings forms that update existing persisted records, add a non-destructive persistence smoke after deploy: fetch the current record, PATCH/PUT the exact same editable values back, and verify a 2xx response plus unchanged returned fields. This proves the route, validation, and table write path work without mutating live business data.
  - Before any Vite SPA rebuild, check for stale `VITE_*` env vars in the shell that could silently flip unrelated features. For Komuna, `VITE_NEON_AUTH_URL` must NOT be set when local basic auth is intended — run `unset VITE_NEON_AUTH_URL` or prefix the build with `env -u VITE_NEON_AUTH_URL npm run build`. After deploy, verify unrelated behavior (like the login page) hasn't changed, not just the changed feature. See `references/vite-rebuild-env-pollution.md`.
  - Run backend tests and backend build.
   - When asked whether a frontend has been fully migrated to a design system/library (for example shadcn/ui), audit the actual integration markers, not just visual class names: package dependencies, config files such as `components.json`/Tailwind config, generated `components/ui/*` files, **active production imports/rendered call sites**, and remaining custom CSS. ## Pitfalls

- **Nested drag/drop children need rendered sibling rows, not just flattened data**: When making subtasks/children independently draggable, a passing build and flattened arrays are not enough. If the child is still rendered inside the parent's draggable/drag-handle subtree, the parent can capture the drag and the child will not move independently. Separate children that should drag into sibling `Draggable` rows, keep only non-independent children nested/collapsed, and update both the child’s visible status and its context association (e.g. current day/goal id) in one mutation plus local cache update.
- **Backend port/migration: reference the original schema first**: When replacing a backend (e.g., Node.js → Go), always retrieve the original DB schema from the old codebase (git history if deleted) before designing the new one. Do not improvise a simplified version (e.g., JSON blob) when the original had a proper relational design with FKs, CHECKs, and indexes. The user expects the new backend to match the original data model.
- **Go switch-case routing MUST `return` after each handler**: Without explicit `return`, execution falls through to the auth middleware which writes a second response on top of the first — producing unparseable concatenated JSON. Every public route case needs `return` before the `requireAuth` block. Also, path trimming needs both `/api/v1` and `api/v1` variants when mixing `mux.HandleFunc` registrations. See `references/go-single-file-api-routing-pitfalls.md`.
- **modernc.org/sqlite "out of memory (14)" = file permission error**: The pure-Go SQLite driver reports permission errors as OOM. When a systemd service running as a non-root user can't write to the data directory, fix with `chown` — don't chase memory issues. See `references/go-single-file-api-routing-pitfalls.md`.
- **Nested SQLite queries deadlock with `SetMaxOpenConns(1)`**: When using a single SQLite connection, you cannot open a second query while iterating a result set. Collect all rows into a slice first, close the rows, then run sub-queries in a second pass. Applies to Go + modernc.org/sqlite.
- **Empty string ≠ NULL for FK columns**: SQLite treats empty string as a valid value but fails FK checks if the referenced table uses UUID PKs. Always convert empty strings to `nil` before inserting into nullable FK columns.
- **Bulk migration with FKs**: Disable `PRAGMA foreign_keys=OFF` during bulk data migration, then re-enable after. Otherwise FK constraint failures on intermediate states will abort the migration.
- **Dead-code Go migration trap**: In layered Go monorepos, `main()` may call `models.Migrate()` from `internal/models/` while `db.go` has a same-named `app.migrate()` that is never invoked. Always trace the actual startup call chain before patching migration code. See `references/go-layered-migration-dead-code.md`.
