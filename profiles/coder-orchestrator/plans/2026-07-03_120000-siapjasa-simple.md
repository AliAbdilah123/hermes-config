# SiapJasa Simple — Implementation Plan

> **For Hermes:** Use full-stack-feature-implementation skill. Dispatch subagents for parallel work, keep final integration + deployment in parent.

**Goal:** Create "siapjasa-simple" — a customer-oriented bounty marketplace where users post "butuh jasa" (gigs/bounties) and others submit proposals. Based on the multi-tenant SaaS boilerplate, stripped of multi-tenancy and payment plugins. Single-user app with bank detail onboarding, email verification gates, manual-payment coordination, one-image attachments, quota management, and gig status flow.

**Architecture:** Go + SQLite backend with plugin runtime (kept from boilerplate), React/Vite/shadcn frontend. Auth-basic plugin retained and simplified (no tenant creation on registration). New `siapjasa-core` plugin for the bounty marketplace domain. Single user = no tenant concept.

**Tech Stack:** Go 1.22, SQLite (modernc.org/sqlite), React 19, Tailwind v4, shadcn/ui, Vitest, TypeScript.
## Confirmed Requirement Amendments (2026-07-03)

- Payments are **manual** this phase and handled outside the app. Bank details are only user profile/onboarding data; approving a proposal does not expose or manage bank details in this phase.
- Currency is **Rupiah only**.
- Email verification is required before a user can post a gig or submit proposal.
- Bounty/gig and proposal each support **one optional image attachment**, max **5MB**, image-only.
- Gig statuses are: `unpublished`, `open_submission`, `closed_submission`, `finished`.
- Gig has duration fields: `start_at` and `end_at`, entered with datetime pickers in the posting form.
- Poster can decline approved proposals and optionally reopen the gig to `open_submission` to fill quota.
- Poster can increase quota and optionally reopen the gig to `open_submission`.
- If poster manually approves proposals while quota is full, UI must warn; if confirmed, quota increases by the additional approvals.

```sql
CREATE TABLE IF NOT EXISTS bank_details (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  bank_name TEXT NOT NULL,
  account_number TEXT NOT NULL,
  account_holder_name TEXT NOT NULL,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(user_id, account_number)
);

-- Bounties (butuh jasa)
CREATE TABLE IF NOT EXISTS bounties (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  creator_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title TEXT NOT NULL,
  description TEXT NOT NULL DEFAULT '',
  pay_per_task INTEGER NOT NULL,              -- Rupiah integer amount
  quota INTEGER NOT NULL DEFAULT 1,
  start_at TEXT NOT NULL,                      -- RFC3339 datetime
  end_at TEXT NOT NULL,                        -- RFC3339 datetime, must be after start_at
  success_criteria TEXT NOT NULL DEFAULT '',
  status TEXT NOT NULL DEFAULT 'unpublished' CHECK(status IN ('unpublished', 'open_submission', 'closed_submission', 'finished')),
  image_path TEXT,                             -- one optional image, server-validated max 5MB
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_bounties_status ON bounties(status, created_at);
CREATE INDEX IF NOT EXISTS idx_bounties_creator ON bounties(creator_id);

-- Proposals
CREATE TABLE IF NOT EXISTS proposals (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  bounty_id INTEGER NOT NULL REFERENCES bounties(id) ON DELETE CASCADE,
  proposer_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  cover_letter TEXT NOT NULL DEFAULT '',
  proposed_fee INTEGER,                       -- NULL = accepts gig pay_per_task
  image_path TEXT,                            -- one optional image, server-validated max 5MB
  status TEXT NOT NULL DEFAULT 'pending' CHECK(status IN ('pending', 'approved', 'declined')),
  approved_at TEXT,
  declined_at TEXT,
  created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_proposals_bounty ON proposals(bounty_id, status);
CREATE INDEX IF NOT EXISTS idx_proposals_proposer ON proposals(proposer_id);

-- Manual payment helper: poster views approved proposers' bank details for bank transfer.
-- No payment gateway in this phase.

-- Attachment validation rules:
-- Store uploaded images under /opt/siapjasa-simple/uploads/.
-- Accept image/jpeg, image/png, image/webp only; max 5MB; exactly one optional image per bounty and per proposal.
```

### Task 3.3: Write `plugin.go` — plugin manifest + registration
```go
package siapjasacore

type Config struct{}

type Dependencies struct {
    DB          *sql.DB
    Config      Config
    Auth        services.AuthService
    AddMigration func(coreplugin.Context, string, string, string) error
    JSONHandler  func(func(*http.Request) (any, int)) http.HandlerFunc
    WriteJSON    func(http.ResponseWriter, int, any)
    WriteError   func(http.ResponseWriter, int, string)
    DecodeJSON   func(http.ResponseWriter, *http.Request, any) bool
}

type Plugin struct{ deps Dependencies }

func (p Plugin) Manifest() coreplugin.Manifest {
    return coreplugin.Manifest{
        ID: "com.siapjasa.core", Name: "SiapJasa Core", Version: "1.0.0",
        Requires: []coreplugin.Dependency{{ID: "com.boilerplate.auth.basic", Version: ">=1.0.0"}},
        Provides: []string{"bounty.manager", "proposal.manager"},
    }
}

func (p Plugin) Register(ctx coreplugin.Context) error {
    // embed migration SQL
    // Register routes:
    mux := ctx.Router()
    // Bank details
    mux.HandleFunc("/api/v1/me/bank-details", p.handleBankDetails)
    mux.HandleFunc("/api/v1/me/bank-details/", p.handleBankDetailByID)
    // Bounties
    mux.HandleFunc("/api/v1/bounties", p.handleBounties)
    mux.HandleFunc("/api/v1/bounties/", p.handleBountyByID)
    // Proposals
    mux.HandleFunc("/api/v1/bounties/.../proposals", p.handleProposals) // or explicit routing
    mux.HandleFunc("/api/v1/proposals/mine", p.handleMyProposals)
    return nil
}
```

### Task 3.7: Write `handlers.go` — proposal acceptance
```
POST   /api/v1/bounties/:id/approve/:proposal_id → approve proposal manually
POST   /api/v1/bounties/:id/decline/:proposal_id → decline approved/pending proposal
POST   /api/v1/bounties/:id/quota                → increase quota; optionally reopen submissions
```

Approval rules:
- No auto-payment this phase. Manual payment happens outside the app. The app only manages proposal approval/decline and user profile bank-detail forms.
- Approving proposals increments the approved count. If quota is full, backend requires `confirm_over_quota=true`; when confirmed, quota increases by the number of extra approved proposals.
- Declining an approved proposal decrements approved count and may optionally set gig status back to `open_submission` to fill the quota.
- Increasing quota may optionally set gig status back to `open_submission`.
- When approved_count >= quota, system recommends `closed_submission`, but the poster controls reopening.

## Data Flow Summary

```
User Registration → /api/v1/auth/register → users table
  ↓
Onboarding → /api/v1/me/bank-details (POST) → bank_details table
  ↓
Browse → GET /api/v1/bounties → bounties table (status=open)
  ↓
Create Bounty → POST /api/v1/bounties → bounties table
  ↓
Submit Proposal → POST /api/v1/bounties/:id/proposals → proposals table
  ↓ (gate: must have bank_details)
Accept Proposal:
  - FIFO: POST /api/v1/bounties/:id/accept/:pid → bounty_acceptances + updates proposals.status + bounty.status=in_progress
  - Buy: same endpoint but requires payment (ponytail: stub payment record, real payment gateway later)
```

## Acceptance Criteria

1. User can register with email + password (no tenant)
2. On first login, user is prompted to add bank details
3. User cannot submit proposal until bank details are filled
4. Verified user can post unpublished "butuh jasa" with title, description, pay in Rupiah, quota, start/end datetime, success criteria, and optional image
5. User can publish gig to open_submission and browse/search open_submission gigs
6. Verified user with bank details can submit proposal with cover letter, optional fee, and optional image
7. Bounty creator can approve proposals up to quota; over-quota approval shows warning and increases quota only after confirmation
8. Poster can decline approved proposals and optionally reopen status to open_submission to fill quota
9. Poster can increase quota and optionally reopen status to open_submission
11. User can manage multiple bank details
12. User can see their own bounties and proposals in profile

## Risks & Open Questions

1. **Payments**: Payments are manual and outside the app this phase. The app does not expose approved proposers' bank details as an approval/payment artifact. No payment gateway yet.
2. **Currency**: Rupiah only. Store integer Rupiah values.
3. **Email verification**: Required before posting a gig or submitting a proposal. MVP can return verification token/link directly until an email provider is wired.
4. **Notifications**: No notification system yet. ponytail: add when proposal/approval events need real-time updates.
5. **Search**: Basic LIKE-based title search. ponytail: add FTS5 when gig count > 1000.
6. **File uploads**: One image per bounty and one image per proposal, max 5MB, image/jpeg|png|webp only.
